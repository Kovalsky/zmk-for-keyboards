# Монітор Samsung ViewFinity S8 (S80UD) — керування входами та KVM

Дослідження 2026-07-03: чи можна перемикати входи монітора з клавіатури/скриптами,
без фізичної кнопки. Тут — повна мапа того, що вміє і чого не вміє прошивка.

## Залізо

- **Монітор:** Samsung LS32D80xU (ViewFinity S8, серія S80UD, 32", 4K), серійник HNBY900014.
  Входи: HDMI, DisplayPort, USB-C (DisplayPort Alt Mode + 90 Вт живлення). USB-хаб + LAN, вбудований KVM.
- **Ubuntu-ноут (Lenovo):** підключений по **HDMI** (та окремим кабелем до USB-хаба монітора — через нього мишка).
- **MacBook Pro (Intel, macOS 15):** підключений по **USB-C** (відео + USB одним кабелем). У мережі: `MacBook-Pro-Bohdan.local`, SSH увімкнений, користувач `falco`.
- **Клавіатура Lily58:** Bluetooth, окремі профілі для ноута і Mac'а (перемикається своїми BT-клавішами, через KVM монітора не проходить).

## Керування по DDC/CI (з Ubuntu-ноута)

DDC/CI — протокол керування монітором прямо через відеокабель. Інструмент: `ddcutil`
(потрібна група `i2c`; монітор живе на шині `/dev/i2c-4`, прив'язаній до HDMI-порта ноута).

Регістр перемикання входів — VCP-код 0x60. Значення **цього конкретного монітора**
(нестандартні, список у `capabilities` бреше):

| Значення | Вхід | Запис працює? |
|---|---|---|
| `0x05` | HDMI (Ubuntu-ноут) | ✅ так, з будь-якого стану |
| `0x01` | USB-C (Mac) | ❌ **тільки читається**; запис ігнорується |
| `0x0f` | DisplayPort (порожній) | ✅ так |
| `0x06` | «HDMI2» — фантом прошивки, фізичного порта нема | ✅ так (екран «no signal») |

Корисні команди:

```bash
ddcutil --bus 4 getvcp 60          # який вхід зараз активний
ddcutil --bus 4 setvcp 60 0x05     # повернутись на Ubuntu-ноут — ПРАЦЮЄ ЗАВЖДИ,
                                   # навіть коли монітор показує Mac
```

## Головний висновок: перемкнутись НА Mac командою неможливо

Прошивка приймає команду «піти з USB-C», але ігнорує «перейти на USB-C». Вичерпно перевірено:

- всі 255 значень VCP 60 записом з HDMI-каналу (+ двобайтові варіанти) — приймаються лише три з таблиці вище;
- те саме з DP-входу і в режимі PIP/PBP — ігнорується скрізь;
- повний дамп усіх ~41 читабельних регістрів у станах «активний ноут» vs «активний Mac»:
  відрізняються лише VCP 60 та яскравість → прихованого вендорського перемикача нема;
- стан PIP/PBP у DDC-регістрах не відображається взагалі (дамп до/після — ідентичний);
- запис з боку Mac'а (через його USB-C-канал): **транспорт мертвий** — і `ddcctl`
  («Failed to send DDC command»), і BetterDisplay CLI (яскравість working, будь-який DDC — «Failed.»);
- мануал (BN81-25930A, 49 стор.) прочитаний повністю: інших каналів керування
  (мережа, RS-232, CEC) модель не має; «Easy Setting Box» — то лише тайлінг вікон.

## Що працює насправді

- **Mac → Ubuntu:** чиста DDC-команда `setvcp 60 0x05` з ноута (~1–2 с). Ноут може її
  виконати завжди, бо його DDC-канал по HDMI монітор тримає живим навіть неактивним.
- **Ubuntu → Mac:** єдиний робочий обхід — «переподати» відеосигнал Mac'а, щоб спрацювала
  опція монітора **Auto Source Switch+** («нове підключене джерело показується автоматично»):

  ```bash
  ssh falco@MacBook-Pro-Bohdan.local 'pmset displaysleepnow'
  sleep 2
  ssh falco@MacBook-Pro-Bohdan.local 'caffeinate -u -t 3'
  # монітор сам стрибає на Mac через ~2–4 с після пробудження; KVM забирає і мишку
  ```

  Таймінги критичні: пауза між сном і пробудженням < ~2 с — лінк не встигає розірватись,
  перемикання не відбувається. Повна затримка до картинки ~6–8 с — фізична межа
  (переузгодження DP-лінка), швидше вміє тільки фізична кнопка (там сигнал уже живий).

- Потрібні опції в меню монітора (обидві були ввімкнені з коробки):
  **System → Auto Source Switch+ → On** і **USB-C Switch → On**.

## Граблі, на які вже наступили

- «Вимкнути HDMI ноута і хай монітор сам знайде Mac» — НЕ працює: без сигналу монітор
  просто засинає, а не шукає інші входи (мишка при цьому «зникає» через сон хаба — не
  плутати з KVM-перемиканням).
- Кнопкове меню Source ховає порти без сигналу — тому порядок у ньому «плаває».
- macOS ігнорує повторні `pmset displaysleepnow` підряд (дебаунс) — між спробами треба пауза.
- `m1ddc` — тільки для Apple Silicon; на Intel-Mac — `ddcctl` (але DDC на macOS 15 у нього мертвий).

## РОЗВ'ЯЗАНО (2026-07-03): Mac на DisplayPort — перевірено наживо

Блок стосується лише переходу **на USB-C-вхід**. HDMI (`0x05`) і DP (`0x0f`) командам
підкоряються. Рішення: Mac під'єднано кабелем **USB-C→DisplayPort** у DP-порт монітора.
Обидва напрямки — однією DDC-командою з Ubuntu, миттєво, без SSH і без переподачі відео:

- **Ubuntu → Mac:** `ddcutil --bus 4 setvcp 60 0x0f` (у скрипт — з повтором до підтвердження
  реєстру: на Samsung перемикання на DP іноді з 2-3 спроби, ddcutil issue #398).
- **Mac → Ubuntu:** `ddcutil --bus 4 setvcp 60 0x05`.

Обидві команди виконує **Ubuntu-ноут** — його DDC-канал по HDMI живий завжди, навіть коли
монітор показує Mac.

Робоча конфігурація монітора (виставлено і перевірено):
- **System → USB Source Setup:** `HDMI → USB-B`, `DisplayPort → USB-C`. Так хаб (миша) їде
  за активним відеовходом: HDMI→Ubuntu, DisplayPort→Mac.
- **System → Auto Source Switch+ → Off** (щоб не стрибав на живий, але заблокований USB-C-вхід).
- Кабелі Mac'а: USB-C→DP (відео на DP-вхід) + звичайний USB-C (дані для KVM + 90 Вт заряду).
  На USB-C-вході лишається фантомний сигнал — просто не вибираємо його.

Перевірка (обидва боки, об'єктивно):
- `setvcp 0x0f` → миша зникла з `lsusb` Ubuntu за 1 с і з'явилась у `ioreg` на Mac'у.
- `setvcp 0x05` → миша повернулась на Ubuntu за 1 с.

Mac = MacBookPro15,1 (2018 15", Intel i9), лише Thunderbolt/USB-C. Який з 4 портів — байдуже:
блок на USB-C-вході монітора, не на порту Mac'а.

## Розбудити сплячий Mac по Wi-Fi (перевірено journal-ом Mac'а)

Повне вимкнення (Shut Down) → розбудити по мережі НЕМОЖЛИВО (вендор-підтверджено: WoL
на Mac будить лише зі сну, ніколи з power-off). Тому «інколи вимикати Mac» = використовувати
**Сон**, не Shut Down.

Зі СНУ по Wi-Fi будиться, але у два кроки (перевірено `pmset -g log`):
1. **Магічний пакет (WoL)** на Wi-Fi-MAC → лише DarkWake (мережа встає, але екран лишається
   вимкнений, через ~9с сон назад). Сам по собі недостатній.
2. Одразу **`caffeinate -u`** по SSH → повне пробудження: у журналі «Display is turned on» +
   «Wake … EC.ARPT/HID Activity», `CurrentPowerState=4`. Аж тоді `setvcp 60 0x0f`.

Умови (усі виконані): Apple TV «Living Room» (192.168.0.113) у мережі як Bonjour sleep-proxy;
Mac на живленні (WoL з батареї ненадійний); `pmset womp=1`; Remote Login увімкнено.
Wi-Fi-MAC Mac'а = `4e:b2:55:a3:78:18` (приватна адреса; апаратний `a4:83:e7:1f:e9:ac`).
БЕЗ Apple TV у мережі Wi-Fi-пробудження ненадійне. Ethernet вирішив би надійно, але користувач — тільки Wi-Fi.

`to-mac` для сплячого Mac'а: WoL-пакет → цикл SSH до конекту → `caffeinate -u -t N` →
`setvcp 60 0x0f`. Коли Mac уже не спить (clamshell-робота) — WoL/caffeinate миттєві no-op,
лишається тільки setvcp. ~5-8с зі сну, миттєво коли не спить.

## Зроблено (2026-07-04): хоткеї зібрані — обидва боки

Фінальний дизайн — **два Lily-акорди** (по одному на напрям), на шарі ADJUST
(тримати обидва thumb'и, поряд з BT-клавішами): `→MAC` і `→UBU`. Кожен = tap
вільного F-коду → пауза 300 мс (щоб HID-звіт долетів до поточного хоста) →
`&bt BT_SEL`. Коди вільні: F6/F7/F9 = диктовка, F2/F4/F8 = meeting, F13 = LOWER;
взято **F16 (→MAC)** і **F17 (→UBU)**. BT-профілі: **BT1 = профіль 0 = Ubuntu,
BT2 = профіль 1 = Mac**.

**Ubuntu → Mac** (`kvm_to_mac` = F16 → `&bt BT_SEL 1`):
- Lily на Ubuntu шле F16 → evdev-листенер `~/tools/mon-kvm/hotkey-listener.py`
  (юніт `mon-kvm-hotkey.service`, дзеркалить whisper-dictate) → запускає
  `~/.local/bin/mon-to-mac`; сам акорд перемикає BT на Mac.
- `mon-to-mac`: WoL (inline-python, обидва Wi-Fi-MAC, UDP-broadcast :9) → цикл
  `ssh falco@mac 'caffeinate -u'` до конекту (≤25 с) → `mon-ddc-set 0x0f`.

**Mac → Ubuntu** (`kvm_to_laptop` = F17 → `&bt BT_SEL 0`):
- Lily на Mac шле F17 → Karabiner (правило scoped на Lily vendor 7504 / product
  24926) → `ssh b_bondar@BS-00012.local /home/b_bondar/.local/bin/mon-to-laptop`;
  сам акорд перемикає BT на Ubuntu.
- `mon-to-laptop` → `mon-ddc-set 0x05` (Ubuntu завжди активний — будити нема кого).

Спільний хелпер `~/.local/bin/mon-ddc-set 0x05|0x0f`: `setvcp` у циклі до
підтвердження через `getvcp` (Samsung DP flaky, #398). ddcutil потребує групи
`i2c` — якщо контекст її не має (сесія/юніт стартували до додавання групи),
скрипт сам re-exec під `sg i2c` (user — член групи, пароль не питається).

**Щоб увімкнути реверс (Mac→Ubuntu) — кроки user'а:**
- `sudo apt install openssh-server && sudo systemctl enable --now ssh` — sshd на
  Ubuntu **не був встановлений** (не просто inactive). Ключ Mac'а `id_ed25519` вже
  дописаний у `~/.ssh/authorized_keys` тут.
- Mac: Wi-Fi → **Private Wi-Fi Address → Fixed** (ротація MAC ламає WoL);
  Apple TV «Living Room» увімкнений (Bonjour sleep-proxy).
- Перепрошити обидві половини Lily (keymap уже містить макроси + ADJUST-клавіші;
  workflow — пам'ять `feedback_download_builds`).
